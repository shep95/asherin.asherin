PURPOSE
Unify idea -> narrative -> code, code -> narrative -> code, whole-architecture repair, a 100-domain engineering taxonomy, 28 specialized software profiles, 50 senior engineering patterns, 80 vibe-coded anti-patterns, and implementation/verification contracts.

EVIDENCE BOUNDARY
All entries are design proposals and engineering heuristics, not empirical assertions that they detect authorship or guarantee correctness. An anti-pattern is identified by verified behavior and consequences, not by superficial style or the suspected use of AI. Different systems require different checks.

UNIVERSAL OPERATING RULE
Discover -> model -> diagnose -> trace -> repair -> verify -> record.
The engine must not report completion until relevant acceptance conditions have been verified, and must disclose unverified behavior and missing dependencies.

PART I — CONCEPTUAL FOUNDATION

A. TWO ORIGINAL PATHWAYS
1. code -> narrative -> code: reverse-engineer existing software into an implementation-independent account of its behavior and architecture; reconstruct, repair or migrate code while preserving required behavior.
2. idea -> narrative -> code: extract intent and requirements from an idea; produce a structured, testable narrative and generate code from it.
3. code -> narrative -> reasoning -> code: extend reconstruction with explicit constraint, architecture and security analysis.
4. narrative -> code -> observed narrative: compare intended behavior with observed implementation to find divergence.
5. complete feedback cycle: idea -> narrative -> code -> observed behavior -> narrative comparison -> code repair.

B. NARRATIVE CONTENT
- identity: system purpose and scope
- actors: humans, services and external systems
- behavior: triggers, operations and effects
- state: owned and mutable information, state transitions
- constraints: invariants and non-permitted outcomes
- outcomes: success, failure, recovery

C. TWO SYNCHRONIZED FORMS
human narrative: comprehensible natural-language explanation of behavior and constraints.
machine narrative: structured contract containing typed inputs, outputs, states, transitions, preconditions, effects, invariants and failure paths.

D. EXAMPLE: CART ADDITION
human: a customer can add a product to their cart only when sufficient inventory exists. adding to cart does not reserve inventory until checkout.
structured conceptual record:
actor: customer
action: add_to_cart
inputs: product_id, quantity
preconditions: quantity > 0, product_exists, available_inventory >= quantity
effects: cart_item_quantity_increases, inventory_unchanged
failure: reject_invalid_quantity, reject_insufficient_inventory
invariant: cart_addition_never_reserves_stock

E. ARCHITECTURAL ENGINES
01 semantic extractor: extract meaningful requirements from idea or code
02 narrative constructor: express behavior, causality and rules
03 structural modeler: build states, workflows, data, interfaces and dependencies
04 reasoning engine: identify contradictions, omissions and tradeoffs
05 code synthesizer: generate executable implementations from validated models
06 verification engine: test runtime behavior, contracts, security and requirements
07 recursive refinement: revise narrative and code based on verified results

F. KEY PRINCIPLE
Narrative should be a durable versioned intermediate representation. Code, tests, documentation, schemas and deployment configuration can be generated or maintained as related expressions of the narrative where technically feasible. Intended narrative must not be silently rewritten to excuse implementation errors.

PART II — WHOLE-ARCHITECTURE REPAIR TAXONOMY

FIVE QUESTIONS
1 what exists? components, boundaries, state and dependencies
2 what should exist? verified intent, contracts and requirements
3 what is broken? observed violations and behavioral mismatch
4 why is it broken? evidence-backed underlying causal mechanism
5 how can it be repaired and verified? viable intervention and explicit tests

TWELVE CORE REPAIR DOMAINS
01 semantic: misinterpreted purpose or behavior
02 requirements: omitted, contradictory or unimplemented expectations
03 structural: faulty boundaries, decomposition, coupling and cohesion
04 dependency: cycles, incompatible components and cascading failures
05 behavioral: incorrect workflows, conditions and outputs
06 state: ownership, races, invalid transitions and lifecycle errors
07 data: schemas, integrity, data loss, transformations and migration errors
08 interface: broken inter-component and external contracts
09 security: broken trust boundaries, auth, injection, secrets and access policy
10 execution: runtime, resource, timeout and concurrent execution defects
11 performance: latency, complexity, memory and scaling constraints
12 verification: inadequate tests, erroneous assumptions and architecture drift

DIAGNOSTIC LEVELS
level 1 domain classification: what component or field is affected?
level 2 failure classification: what requirement or invariant is violated?
level 3 causal classification: what mechanism produces that failure?
level 4 repair classification: what verified change eliminates the cause?

RELATIONSHIP TYPES
depends_on, calls, owns_state, reads_from, writes_to, implements, constrained_by, trusts, verified_by, violates, caused_by.
Relationships form a graph of effects and responsibilities. Causation must be supported by evidence rather than inferred from mere dependency.

REPAIR MODES
local correction: isolated defect
contract repair: inconsistent interfaces or guarantees
boundary repair: misassigned trust or responsibility
state consolidation: conflicting authoritative state ownership
dependency restructuring: faulty coupling/direction
component replacement: existing module cannot meet required contract
architectural migration: fundamental structure must change
requirement reconciliation: contradictory or incomplete intended behavior

EVIDENCE STATUS
observed: supported by inspectable execution/code evidence
inferred: strongly suggested but not proven
hypothesized: plausible explanation needing test
contradicted: inconsistent with better evidence
unknown: insufficient information
verified: specifically passed a defined acceptance condition

SIX PHASES
1 reconstruct: inventory and model actual code behavior
2 classify: build responsibility/dependency graph; tag failures
3 trace: evaluate causal chains and competing hypotheses
4 repair: select bounded changes compatible with preserved constraints
5 verify: execute targeted, integration, regression and risk tests
6 reconcile: re-extract observed narrative, compare and repeat if needed

REPAIR ACCEPTANCE
- originally identified failure does not reproduce under relevant conditions
- underlying causal mechanism addressed, not concealed
- previously required behavior remains satisfied
- related dependencies and trust boundaries remain valid
- intended and observed narratives agree on verified claims
Unverifiable claims remain explicitly marked partial or unknown.

PART VII — SENIOR ENGINEERING DECISION CONTRASTS

senior: system model before implementation | avoid: files generated without interaction model
senior: analyze irreversible decisions | avoid: committing schema/API/auth without migration assessment
senior: attention proportional to risk | avoid: uniform review across low/high consequence
senior: falsify assumptions | avoid: treating plausible architecture as established
senior: measurable acceptance criteria | avoid: compilation mistaken for completion
senior: runtime-evidence optimization | avoid: speculative performance tuning
senior: justified abstraction | avoid: generic classes as a mark of sophistication
senior: explicit error paths | avoid: only success cases
senior: dependency impact analysis | avoid: patching first reported file
senior: preserve rationale and history | avoid: unexplained rewrites

REVERSIBILITY PRINCIPLE
Examine high-cost-to-reverse decisions more carefully (schemas, public APIs, identity schemes, event contracts, storage formats, domain semantics). Low-cost reversible decisions should not receive unnecessary architectural ceremony. Classification is context dependent.

PART VIII — REGISTRY SCHEMA AND DOMAIN EXECUTION CONTRACT

Every pattern record should include:
pattern_id, name, classification, domain, applicability, trigger, underlying_mechanism, detection_method, evidence, false_positive_conditions, severity, remediation, verification, dependencies, provenance, status.

Every software-domain record should include:
domain_id, family, description, domain_objects, applicability_predicates, relationship_types, invariants, failure_classes, diagnostics, repair_operations, verification_methods, confidence_or_evidence_status.

DOMAIN EXECUTION CONTRACT
1 discover components, actors, interfaces and evidence
2 model intended and observed behavior
3 diagnose violations, inconsistencies and uncertainty
4 trace effects through typed dependency and causality relationships
5 select minimally sufficient corrective changes
6 verify with tests, instrumentation or formal analysis where feasible
7 record the evidence, unresolved conditions and result

APPLICABILITY GATE
Activate a taxonomy domain only when characteristics or failure evidence justify it; do not blindly run all 128 classifications on every project. Cross-domain findings require meaningful linkage and evidence.

EXAMPLE — DUPLICATE PAYMENT
observed: users report repeat charges
networking: timeout after provider may have processed request
execution: retries submit duplicate requests
state: no consistent operation identity
architecture: no enforced idempotency boundary
repair candidate: durable idempotency policy compatible with provider semantics and reconciliation for uncertain outcomes
verification: repeated concurrent and timeout scenarios with provider-independent evidence; do not claim fix based on UI behavior alone.

EXAMPLE — AUTHENTICATION STATE
observed: sessions terminate unexpectedly
state: services disagree on validity
dependency: inconsistent session stores or clocks may contribute
structural: no clear authoritative policy can be a root cause
repair: determine verified cause, establish correct authority/validation mechanism, run expiry, invalidation and cross-service regression tests.

EXAMPLE — INTENT VS OBSERVED NARRATIVE
intended: only admins can delete user accounts
observed: an authenticated non-admin can invoke deletion endpoint
mismatch: authorization invariant violated
repair: enforce policy at authoritative boundary
verify: non-admin denied; admin permitted; associated logging and ownership policies remain consistent.

PART IX — FORMALIZATION AND QUALITY GATES

CONCEPTUAL TRANSFORM
I --E--> N --G--> C
I: idea or existing code
E: extraction and semantic modeling
N: structured narrative intermediate representation
G: architectural translation and generation
C: executable implementation

VERIFICATION FUNCTION
V(C,N) -> {pass, fail, unknown}
Meaning: evaluate actual implementation against explicit, testable narrative clauses. A passing test is not a mathematical guarantee of equivalence for arbitrary software.

QUALITY OPTIMIZATION (CONCEPTUAL)
min over C of [L_behavior + L_constraints + L_implementation]
Loss functions and weighting must be project-specific and evidence-backed, not arbitrary universal scores.

TEN REVIEW GATES
01 all required functions have actual implementations
02 behavior is traceable to requirements and tests
03 architecture has explicit component/state ownership
04 external integrations use real contracts and honest error reporting
05 security boundaries and policy enforcement have been checked
06 important edge cases, recovery and cancellation tested
07 performance requirements supported by measurements
08 builds/dependencies reproducible
09 implementation compared with intended narrative
10 defects and unverified conditions disclosed

NO-FALSE-COMPLETION RULE
Do not mark work complete solely because it compiles, looks polished, returns success, or passes limited tests. Label each feature functional, partially functional, unimplemented or externally blocked with supporting evidence.

BOUNDARY OF COVERAGE
100 core domains + 28 application profiles is a practical, extensible classification, not a logically exhaustive enumeration of all software specializations. The 50/80 engineering patterns are diagnostic seed libraries, not mutually exclusive or exhaustive laws. A pattern should not be flagged automatically from a word, identifier, line count, rerender, or file shape alone.
